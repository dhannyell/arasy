# 2.5D: Projection, Planes, Height And Depth Order

**The default is 2D, and everything on this page is optional.** A `Camera{}`
looks straight down, a `BaseSprite{}` behaves exactly as it always has, and a
game that never mentions the fields below pays nothing for them existing —
not in API to learn, not in pixels, not in cost per frame. Read on only when
you want a scene to read as a tilted world rather than a flat one.

## The one number: `Camera.DepthScale`

2.5D needs a single declared quantity: how far the camera is tilted away from
straight-down. The camera says it as a **foreshortening** of the world's depth
axis.

```go
cam := render.Camera{
    World:      math2d.NewRect(math2d.Vec2{}, math2d.Vec2{X: 160, Y: 90}),
    Viewport:   math2d.NewRect(math2d.Vec2{}, math2d.Vec2{X: 160, Y: 90}),
    Aspect:     render.AspectFit,
    DepthScale: 0.5,
}
```

`DepthScale` is how much of its depth the ground keeps on screen:

| Value | Meaning |
|---|---|
| `1` (and the zero value) | No tilt. A top-down camera. |
| `0.5` | The classic 2:1 view of pixel-art dimetric projection. |
| `0.25` | A shallow, almost side-on look. |

It is the cosine of the tilt from vertical, so `0.5` is a 60 degree tilt. The
API talks about foreshortening rather than degrees because that is how the
result is usually described: people reach for "2:1", not "60 degrees". Values
outside `(0, 1]` are clamped.

The zero value means `1` rather than "flat as a line", so a `Camera{}` written
before this field existed keeps meaning exactly what it meant.

The foreshortening happens around the centre of the visible world, so changing
it never drags the scene out of frame.

## The general projection: `Camera.View`

`DepthScale` covers the tilt because a tilt is common enough to deserve a
number. It does not cover isometric: squashing the Y axis leaves a rectangle a
rectangle, and isometric rotates **both** world axes onto the screen, which
turns a square into a diamond. That is an affine, and `Camera.View` is where it
lives.

```go
// screenX = (x - y) * 20    screenY = (x + y) * 10
isoView := math2d.Affine{A: 20, C: -20, B: 10, D: 10}

cam := render.Camera{
    World:    view,
    Viewport: view,
    Aspect:   render.AspectFit,
    View:     isoView,
}
```

The zero value is identity, so a game that never mentions the field does not
move a pixel.

**It sits on the camera and not on each sprite, and that is the whole
decision.** A projection is a fact about the viewer. Put it on the sprites and
every consumer of the camera keeps working in the unprojected space and quietly
disagrees with the picture: debug overlays land in the wrong place,
`ScreenToWorld` answers in a space nothing else uses, and every entity has to
be re-placed whenever it moves. Declared on the camera, one line reaches all of
it — and because an affine is invertible, `ScreenToWorld` undoes it, so a click
on a grid tile answers with that tile.

Framing follows the projection: `Camera.World` frames *view* space, and under
a skewing view a square board becomes a diamond whose numbers nobody should
work out by eye. `render.FrameGround(view, groundRect, margin)` does that
arithmetic — the box around the projected corners, plus a fraction of air on
every side.

The world stays a square grid. That is not a style detail: it is the space the
physics can reason about. A court is an axis-aligned rectangle `Config.Bounds`
can describe; projected, the same court is a diamond it could not. Only the
last step before drawing turns squares into diamonds.

`View` and `DepthScale` compose — `View` first, then the tilt — but that is
rarely what anyone wants: an isometric view already encodes its own tilt.

**Backend coverage:** every backend draws a `View` for shapes, images, text,
retained batches and particles. Batch positions use the complete camera
matrix. Sprite corners remain screen-space billboards by default; a
`SpriteInstance` with `ProjectCorners` draws its four world corners through the
camera, which is the ground-tile path. Glyphs and particles remain billboards
and do not shear. `DrawParticles.BaseCommand.Transform` remains a deliberate
command-level exception; the camera itself is complete on every backend.

## Layer parallax

Side-scrollers can keep one camera and declare how each layer follows it:

```go
cam.Parallax = []render.LayerParallax{
    {FromLayer: -20, ToLayer: -20, Factor: math2d.Vec2{X: 0, Y: 0}},   // sky
    {FromLayer: -10, ToLayer: -10, Factor: math2d.Vec2{X: 0.3, Y: 1}}, // hills
    {FromLayer: 0, ToLayer: 10, Factor: math2d.Vec2{X: 1, Y: 1}},      // game
    {FromLayer: 20, ToLayer: 20, Factor: math2d.Vec2{X: 1.3, Y: 1}},  // foreground
}
```

`Factor` is a scroll multiplier around `Anchor`. `1` follows the camera,
`0` stays aligned with the screen, a value below `1` moves more slowly, and a
value above `1` moves faster. The first matching layer range wins. A game can
also call `cam.ForLayer(layer)` when it needs the derived camera for manual
content or picking; normal command emission uses the layer automatically.

Repeating scenery uses `render.WrapOffsets` with the derived camera. A
tilemap must use the same camera when it selects retained chunks:

```go
visible := tilemap.VisibleChunks(&ground, cam.ForLayer(groundLayer))
```

`Camera.Pan` and `Camera.ZoomAt` keep camera movement and zoom in world units,
so all factors remain coherent. Lighting is still evaluated in world space;
keep lit ranges on factor-1 gameplay layers unless the displaced-light effect
is intentionally part of the scene. `examples/parallax` shows the complete
declarative path.

## What foreshortens, and what does not

A tilted camera does two different things, and telling them apart is the whole
idea:

- **Positions** foreshorten. Ten units to the north take up less screen than
  ten units to the east, because north is the direction the camera is looking
  along.
- **Shapes** foreshorten only if they lie in the ground plane. A character
  standing up faces the camera and keeps its full height; a marking painted on
  the floor squashes with the floor.

A sprite says which of the two it is:

```go
world.SetRectSprite(id, scene.RectSprite{
    Rect:       courtBounds,
    BaseSprite: scene.BaseSprite{Plane: scene.PlaneGround}, // a painted court
})

world.SetCircleSprite(id, scene.CircleSprite{
    Radius:     4,
    BaseSprite: scene.BaseSprite{}, // PlaneUpright: a ball, facing the camera
})
```

`PlaneUpright` is the zero value, so no existing sprite changes and a standing
character is the default. `PlaneGround` is for decals, puddles, shadows,
painted markings — anything that lives on the floor.

**The plane applies to `View` too, and that is where it stops being a
detail.** Under a tilt the difference between the two is a squash; under an
isometric view it is the difference between a net standing across the court and
one lying on it like a rug. Working out what shape an upright sprite has to be
given so the camera's projection lands it facing the viewer is the engine's
job, not the game's: an isometric game writes no shear correction of its own.

Both sprites move with the foreshortened ground either way: an upright sprite
that ignored the tilt entirely would drift away from the ground it stands on.

Under an untilted camera the two planes are identical and the field costs
nothing to ignore.

## Height and its shadow

Altitude is a component, and it is simulation state like any other:

```go
world.SpawnBundle(scene.Bundle{
    CircleSprite: &scene.CircleSprite{Radius: 4},
    Height:       &scene.Height{Z: 12},
    Ballistics:   &scene.Ballistics{Gravity: 90, BounceDamping: 0.6, RestVZ: 2},
})
```

How `Height.Z` turns into pixels is `render.Projection`, and the way to build
one is to derive it from the camera and the scene's light:

```go
world.SetProjection(render.GroundProjection(cam, render.ProjectionLight{
    Direction: math2d.Vec2{X: -1, Y: -1}, // where the light comes from
    Tilt:      0.18,                      // 0 overhead, 1 grazes the horizon
    Softness:  0.5,                       // 0 a point source, 1 diffuse
}))
```

That one call fills in everything: how far a unit of height lifts the body up
the screen, how large the ground shadow is, how it shrinks and fades as the
object rises, and which way it leans away from the light.

The lift comes out of the tilt as `tan(acos(DepthScale))`. **With
`DepthScale = 1` the lift is zero**, which looks like a bug and is not: a
camera looking straight down has nowhere on screen to put height. A game that
wants visible height wants a tilted camera.

Under a skewing `View` the view takes over: it already encodes a tilt of its
own, and the rule above would read its neutral `DepthScale` as "no height". So
`GroundProjection` derives two things from it:

- **The direction.** Height has to go up *the screen*. On an isometric grid the
  world direction that does that is neither of the world's axes but the
  diagonal — getting it wrong makes a rising ball drift sideways along a grid
  line. That is `Projection.LiftAxis`.
- **The distance.** One unit of height is worth the view's mean scale in
  pixels, which is the screen length it gives a unit of ground. That is the
  convention that makes a unit cube's three edges come out the same length,
  which is the definition of an isometric projection.

`Projection`'s fields stay public, so a game with its own art direction can
override one of them — `ShadowAlpha`, say — without giving up the derivation
for the rest.

The movement every tactics game hand-rolls on top of this has a name:
`World.Hop(id, target, HopOptions{Duration, Apex})` carries an entity in an
arc — position along the straight line, `Height` peaking halfway through the
flight — and the tween removes itself on landing, so "is it airborne" is
whether the component exists.

### Contact shadow and `ShadowStyle`

By default the shadow only exists while the entity is airborne: at `Z == 0`
it vanishes, and a standing character floats over the scene instead of
belonging to it. The opt-in is a render-only component:

```go
world.SetShadowStyle(id, scene.ShadowStyle{}) // contact shadow, engine look
```

With it, the entity keeps its shadow on the ground — same projection, same
light, full alpha — and hands it over seamlessly the moment it lifts off. The
zero value takes the projection's defaults; the fields adjust the emission
per entity:

```go
world.SetShadowStyle(id, scene.ShadowStyle{
    Scale:   1.5,                  // multiplies the radii; 0 means 1
    Alpha:   0.6,                  // multiplies the alpha; 0 means 1
    Offset:  math2d.Vec2{Y: 0.4},  // ground-space nudge
    Disable: false,                // true removes the automatic shadow
})
```

The geometry still comes from the sprite's footprint —
`ImageSprite.ShadowFootprint` for art with transparent padding — and the
component styles it. `ShadowStyle` never enters `Checksum()`; the authored
`ShadowFootprint` is content, so it enters `ContentChecksum` and never
`SimChecksum`. On a `PlaneGround` sprite the component is a no-op: a decal
lies in the ground and casts no shadow of its own. On a parent with
attachments it styles the composite's one shadow.

## Light over sprites: declared, render-only

The engine does not expose a general-purpose lighting pipeline. Instead, a
game declares the lights it needs. The world stores those declarations and
the layers they affect; the renderer applies the modulation when it emits
sprite commands. Lighting remains outside simulation state:

```go
world.SetAmbientLight(scene.AmbientLight{Color: render.RGBA(0.75, 0.75, 0.85, 1)})
world.SetLitLayers(minLayer, maxLayer) // opt-in; no call means no lighting

torch := world.Spawn()
world.SetTransform(torch, scene.Transform{Position: pos})
world.SetPointLight(torch, scene.PointLight{
    Color:  render.RGBA(0.6, 0.42, 0.18, 1), // contribution at the source
    Radius: 20,                              // no contribution beyond this range
})
```

A `PointLight` has no position field by design. Its position is the entity's
`Transform`, interpolated in the same way as a body's position. A torch
carried by a unit therefore keeps its glow in sync without a second position.
A stationary light is simply an entity with a `Transform` and a
`PointLight`.

For each sprite inside the selected layer range, the renderer adds the
ambient and point-light contributions at the sprite's interpolated ground
position. It clamps each RGB channel to `[0, 1]` and multiplies the result by
the authored color; alpha is unchanged. An attachment uses its parent's
position, so a composite is lit as one body. A `CommandSprite` group follows
the same composite rule: one light value at the entity's position,
multiplied into every color field of its authored commands via
`render.WithLight` — retained batches and particles inside a group pass
through, by the exemptions the guard test records. A point light falls off as
`1 - d²/R²` and reaches zero at `Radius`. Each whole `Falloff` step applies
one additional multiplication; a fractional value blends the two neighboring
curves using the same basic arithmetic. Sprites outside the range, such as
HUD and overlay elements, keep their authored colors.

The renderer modulates the output instead of changing the sprite. Authored
`Color`/`Tint` is simulation state by decision: games can encode game state in
sprite colors, and color tweens are simulation. The authored color therefore
stays in `Checksum`, while lighting never writes to it. Lights follow the same
render-only model as `SpriteTransform`: they are cloned for presentation
continuity and excluded from checksums and replays. Two hosts at the same
tick and alpha produce the same commands because the evaluation uses only
`+ - * /` on frame positions.

Normal maps are **not supported, by decision**. Per-pixel lighting would need
a new shader in every backend (Canvas2D has no shader to program) and a second
authored texture for each sprite. Color modulation is the practical substitute
at this tier. `examples/outpost` consumes the channel with dusk ambient light
over the actors and one warm plaza lantern.

## Depth order: who is drawn behind whom

Sprites are painted back to front. Within a layer, each sprite gets one number
— its **sorting point** projected onto the world's **sort axis** — and lower
draws first, which is to say further away.

### The sorting point is the sprite's base

A sprite sorts by its base, not its centre. That is the difference between a
scene that reads correctly and the single most common y-sort bug: a tall tree
and a short bush planted on the same ground line have centres at very
different depths and bases at the same one, so sorting by centre draws the
tree behind the bush standing next to it.

Each sprite type finds its own base — the bottom of a circle's radius, of a
rect, of an image's size — so mixing types does not reintroduce the problem.
`SortOffset` moves the point from there:

```go
world.SetImageSprite(id, scene.ImageSprite{
    Size:       math2d.Vec2{X: 32, Y: 64},
    SortOffset: math2d.Vec2{Y: -8}, // art whose feet sit above the bottom edge
})
```

`Transform.Scale` deliberately does not enter the base: a sprite that pops or
breathes would otherwise reorder itself in the middle of its own animation.

### The axis is something the world declares

```go
world.SetSortAxis(math2d.Vec2{X: 0, Y: 1}) // plain y-sort, and the default
```

The zero value is `{0, 1}`: further down the screen draws in front, which is
right for a camera looking straight down and is what the engine did before the
axis was something you could say out loud. A tilted camera wants depth weighted
against height; a game that stacks along X wants `{X: 1}`. The vector is a
direction, so its length is ignored and negating it reverses depth.

### Height stays out of it

An entity in the air still sorts by where it stands on the ground. That is
where it is in the world, it is where its shadow is, and it is what lets a ball
pass behind a post while flying past it. Sorting by the lifted position would
snap the ball in front of the post halfway through the arc.

A game that wants the opposite composes it by hand with `Layer`.

### Ties, and why they are ordinary

The key is a `float64`, so two sprites landing on the same value is common
rather than rare — every sprite standing on the same ground line ties. `EntityID`
breaks the tie, which is what makes a frame reproducible: the same scene always
paints the same way, on any host, in any replay.

`SortAxis` and `SortOffset` are presentation. Neither enters `Checksum()`,
snapshots or replay.

### What sorting by a single number cannot do

Reducing a sprite to one scalar has three structural limits. They are written
here so you meet them on this page rather than in a shipped game:

1. **Interpenetration.** Ordering is per command and therefore all-or-nothing:
   a sprite is entirely in front or entirely behind. A character standing *in*
   a doorway, or half behind a fence, has no correct order, because the right
   answer differs per pixel. Only a per-pixel depth buffer resolves this.
2. **Long objects.** A wall ten units deep gets one key, but things at
   different depths along it should order differently against it.
3. **Cycles.** A over B, B over C, C over A. No total order satisfies that.

For the common case — compact sprites (characters, balls, trees, crates) on a
floor — sorting by the base is correct and complete. For the other two, the
standard fix is authoring rather than engine: **slice the long object into
pieces that sort separately**, which is what every 2D game does with walls,
bridges and doorways. `SortOffset` is what makes that cheap, because each piece
can claim its own depth without its sprite having to move.

### Raw-command props: `CommandSprite`

A prop whose shape no built-in sprite can draw — an extruded building, a
faceted mountain — becomes a list of raw commands, and raw commands have no
base to sort by. `CommandSprite` gives them one: the entity joins the painter
sort like any sprite, with its `Transform.Position` (plus `SortOffset`) as
the sorting point, and the commands come out exactly as written, only with
the layer rewritten to the component's, so the group paints as one body.

```go
world.SpawnBundle(scene.Bundle{
    Transform:     &scene.Transform{Position: buildingBase},
    CommandSprite: &scene.CommandSprite{Layer: layerActors, Commands: building},
})
```

The content is presentation: it never enters `Checksum`, and a moving entity
does not move its commands — they are absolute world geometry, like a
`RectSprite`'s `Rect`. Decoration that moves wants an `Attachment`.

### Composite objects: `Attachment`

A tree is a trunk with two canopies; a machine is a body with a glow riding
on it. `Attachment` keeps the set **one thing** in the painter order: the
attached sprite draws at the parent's position (interpolated like the
parent's), climbs `HeightOffset` up the lift axis *on top of* the parent's
own height, sorts exactly at the parent's depth and draws right after it. It
casts no shadow of its own — the parent's marks the ground for the whole
composite.

```go
trunk := world.SpawnBundle(scene.Bundle{ /* Transform + RectSprite */ })
world.SpawnAttached(trunk, math2d.Vec2{}, canopyHeight, scene.Bundle{
    CircleSprite: &scene.CircleSprite{Radius: 2.3, /* ... */},
})
```

Attached geometry is relative to the anchor: an attached `RectSprite`'s
`Rect` is an offset around it, not absolute coordinates.

## What never foreshortens

Foreshortening is a fact about the camera, not about the world. It stays out of:

- **Collision and physics.** Colliders, bounds, bounce and `Ballistics` all
  work in unforeshortened world units. A tilted camera never changes where two
  circles touch.
- **`World.Checksum()`, snapshots, recordings and replay.** `DepthScale`,
  `Plane` and `Projection` are presentation. `Height.Z` *is* simulation state
  and is hashed like everything else — what the projection decides is only how
  it becomes a pixel.
- **Scalar conversions.** `WorldScalarToScreen` is for quantities with no axis
  — stroke widths, corner radii — and ignores the tilt. Radii do have an axis
  and go through `WorldRadiiToScreen`, which is why a circle drawn on the
  ground reaches the screen as an ellipse.

Hit-testing keeps working because `Camera.ScreenToWorld` is the exact inverse
of `WorldToScreen` under any tilt. This matters beyond clicks: recordings
store pointer coordinates, so an asymmetric pair would break replay.

## The choices are independent

Projection, sprite plane and height do not imply one another, and no
combination is invalid:

- Blob shadows with no tilt at all: set the `Projection` fields yourself and
  leave `DepthScale` alone.
- A tilted world that never uses `Height`: set `DepthScale` and nothing else.
- A ground decal in an otherwise flat game: `PlaneGround` with no tilt is
  simply a no-op.

## Worked example

`examples/outpost` is the complete 2.5D example: a square board becomes a
retained tilemap under `Camera.View`, while the island walls and props use the
same projection and the units use `Height`.

### Tilemaps keep presentation outside simulation state

The tilemap package stores a square grid and an atlas layout. It produces
sprite instances per chunk; the game publishes each chunk as a retained
sprite batch. Ground tiles set `ProjectCorners`, so the camera turns their
square world cells into the projected ground shape. The world grid itself
stays square.

Tile data used only for drawing is presentation state. Keep gameplay data in a
`runtime.StateSlot` and derive the `tilemap.Layer` from it when the drawing
needs an update:

```go
type BoardState struct {
	Cells [boardWidth * boardHeight]int16
}

type Game struct {
	runtime.StateSlot[BoardState]
	ground tilemap.Layer // derived presentation data
}
```

A gameplay change updates `StateSlot` first. The game then updates the changed
layer cells, consumes `DirtyChunks`, and replaces only those retained batches.
The layer is not part of the simulation checksum or replay. Rebuilding it
after a snapshot restore therefore cannot change deterministic gameplay.

Under a `View` the same scene keeps its square world grid and puts the whole
projection in one line in `Setup` — even movement, because keys read on the
screen invert back onto the grid through that same `View`.

For the artist, the chosen angle becomes a contract through `arasy stencil`:
the command renders a PNG guide sheet — tile grid, unit cube, lift vector and
shadow — through the same camera and projection the game declares, with the
pixel measurements annotated. The flags mirror the `Setup` fields one for one
(`--view "2:1"` or the raw affine, `--depth-scale`, `--tile` for scale).

Watch out for the isometric-art trap: a sprite is drawn centred on its
position, so standing one on its own feet means moving it up *the screen*, not
along the world's `-Y`. Under a `View` those are different directions, and
taking the world one slides every prop up and to the right of the ground it is
meant to be standing on.

`examples/outpost` is the same foundation used by a full scene: an
isometric island of extruded volumes, with units hopping from tile to tile.

## Camera passes and picking

Each `render.Pass` owns its camera, so the same world can be projected into a
split-screen panel or minimap without moving commands into another coordinate
system. `RenderContext.AddPass` declares extra passes; the base camera still
draws last, keeping debug overlays and UI above them. A minimap is one extra
pass with its own world rectangle and screen viewport:

```go
ctx.AddPass(minimapCamera, worldCommands)
```

Handle UI first when picking. For world picking, rebuild the same pure pass
camera list used by Render, then call `render.CameraForScreenPoint`. It checks
extra passes in reverse declaration order and falls back to the base camera,
so a full-screen base viewport cannot hide a minimap camera:

```go
camera := render.CameraForScreenPoint(baseCamera, passes, screenBounds, pointer)
worldPoint := camera.ScreenToWorld(pointer)
```

## Known limits

- **The shadow is a blob**, and can only be one: altitude is per entity, not
  per pixel. A shadow shaped like the object would need a height value for
  every pixel of the sprite.
- **Shadows do not sort among themselves.** Each shadow is emitted next to the
  body it belongs to so that the depth sort keeps an entity's commands
  together, which means one entity's shadow can fall over a neighbour already
  drawn in the same layer.
- **A very low light throws the shadow far away.** The distance it travels
  grows with height without bound; keep `ProjectionLight.Tilt` modest, or set
  `ShadowEscapePerZ` yourself.
- **Sprites cannot interpenetrate.** A sprite is drawn entirely in front of or
  entirely behind another. Only a per-pixel depth buffer would change that.
- **There is no true vertical face.** A rectangle leaves the camera as a
  diamond (ground) or as an upright billboard, never as the side of a block.
  What exists is the painter's trick with an API name: `Projection.Wall`
  sweeps a ground edge along the lift, and `Projection.ExtrudeRect` assembles
  the whole block — the two faces the projection makes visible plus the top
  lifted by `Projection.LiftVector()`, the same vector that lifts entities
  with `Height`. `examples/outpost` builds an entire island out of it.
- **Particle command transforms are not supported.** `DrawParticles` follows
  the camera's complete `View` and `DepthScale`, but its
  `BaseCommand.Transform` is intentionally ignored. A per-command transform
  would need a separate particle contract and is outside the camera feature.
- **A rounded rect loses its corners on Canvas2D** under a skewing camera:
  `roundRect` cannot draw a parallelogram, and the per-vertex path traces only
  the four corners.
